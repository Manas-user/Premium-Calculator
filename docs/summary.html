1. What is this Project? (In Simple Words)

Premium Calculator is a full-stack web application designed to calculate, manage, and track estimated insurance premiums. More importantly, it is built to demonstrate the complete modern Software Development Lifecycle (SDLC) and DevOps pipeline required in enterprise software engineering:

  • For the Customer/User: A fast, responsive web portal where you enter a customer's name, choose a policy category (Life, Health, Vehicle, Travel), enter a coverage sum and duration, calculate estimated annual and total premiums, and download a text receipt voucher.
  • For Claims Officers: A management dashboard to review submitted transactions, approve or reject them, and maintain an audit history.
  • For the DevOps Engineer / College Evaluation: A complete CI/CD automation suite featuring version control (GitFlow), containerization (Docker), continuous integration (Jenkins and GitHub Actions), configuration management (Ansible), and operational health monitoring (Spring Boot Actuator).
Key Academic Disclaimer: All calculation formulas and rates are demonstration estimates designed for educational grading and do not represent real-world commercial insurance underwriting quotes.

2. What the Application Does (Core Features)

1. Calculate Estimates

Calculates transparent annual and total premiums for 4 policy categories with strict mathematical precision using Java BigDecimal.

2. Transaction Lifecycle

Every calculation is saved with a unique ID (e.g. TXN-A1B2C3D4) in SUBMITTED state, and can be reviewed, approved, or rejected.

3. Instant Receipt Download

Generates an official formatted plain-text receipt voucher (receipt-TXN-XXXXXXXX.txt) ready for download.

4. System Health Heartbeat

Frontend continuously pings the backend Actuator endpoint (/actuator/health) to display a live green status badge (Backend: UP).

Expected Faculty Questions & Model Answers:

Q1: Why did you use BigDecimal instead of double or float for calculations?

Answer: "In financial applications, float and double use binary floating-point representation, which causes imprecise decimal rounding (e.g., 0.1 + 0.2 != 0.3). BigDecimal guarantees exact arbitrary-precision arithmetic. We also enforce RoundingMode.HALF_UP scaled to 2 decimal places to meet currency standards."

Q2: Why is a multi-stage Dockerfile better than a single-stage one?

Answer: "A single-stage Dockerfile retains the entire JDK, Maven compiler, and source code in the final image, making it 800MB+ and vulnerable. In our multi-stage build, Stage 1 builds the JAR with JDK 17, but Stage 2 copies only the compiled JAR into a lightweight, hardened JRE 17 runtime, reducing image size to ~200MB and eliminating build tool attack surfaces."

Q3: Why run the container as a non-root user?

Answer: "By default, containers execute as root. If an attacker exploits an application vulnerability, they could potentially escape container boundaries with root privileges. In our Dockerfile, we explicitly create and switch to appuser:appgroup (UID 1001), adhering to the Principle of Least Privilege."

Q4: What is the purpose of Spring Boot Actuator in your project?

Answer: "Actuator exposes production-grade observability endpoints. We exposed /actuator/health, which returns a structured JSON heartbeat ({"status":"UP"}). This is actively polled by our frontend UI, Docker's HEALTHCHECK directive, the Jenkins deployment stage, and our Ansible playbook to guarantee zero-downtime health verification."

Q5: What branching strategy did you follow in Git?

Answer: "We adopted the GitFlow model using two primary branches: main (for production releases) and develop (for continuous integration and testing). We also followed the Conventional Commits convention (e.g. feat:, chore:, ci:)."
